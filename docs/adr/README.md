# 架构决策记录（ADR）

本目录记录项目中**难以逆转、影响面大**的架构决策，以及当时的权衡。

## 为什么要写 ADR

- 六个月后能回答“当时为什么这么选”。
- 避免同一问题反复讨论。
- 让新增协作者快速理解约束来源。

## 什么算 ADR

需要 ADR

- 分层与模块边界的变化。
- 引入或移除重要第三方依赖。
- 数据格式/存档格式的破坏性变更。
- 线程模型、ECS 语义、序列化策略等全局约定。
- 构建系统与工具链的根本变更。

不需要 ADR

- 局部的类名、函数签名、目录微调。
- 一次性的 bug 修复。
- 可随时改回的小重构。

## 工作流

1. 复制 `template.md` 为 `NNNN-kebab-case-title.md`，编号连续递增。
2. 状态从 `Proposed` 开始。
3. 讨论通过后改为 `Accepted`，同时更新受影响的模块文档与 `docs/index.md`。
4. 决策被取代时，**不改写原文**，将状态改为 `Superseded by ADR-NNNN`，并新增新 ADR。
5. 事实性更正（错字、失效链接）可直接修改。

## 状态定义

| 状态 | 含义 |
|---|---|
| Proposed | 提议中，尚未生效 |
| Accepted | 已采纳，当前实现应遵循 |
| Deprecated | 仍然有效但不再推荐 |
| Superseded | 已被后续 ADR 取代 |
| Rejected | 讨论后否决，保留原因 |

## 约定

- 一个 ADR 只做一个决策。
- 必须写“考虑过的其他方案”，否则无法判断权衡。
- 必须写“后果”，包括负面后果。
- 决策与模块文档冲突时，以 ADR 为准，并修正模块文档。
