# 已知限制与后续改进汇总

> **用途**：把各模块与架构文档里的已知限制集中到一处，作为后续完善程序的检查清单。
> 这里只汇总「还没做 / 做得不完整」的内容；已修掉的坑不重复抄录。
>
> **维护方式**：每次交付后，把对应模块的新限制加入本文件；如果某项已修复，直接删除或标记为已完成。
> **来源**：`docs/status/plan-status.md`、`docs/architecture/*.md`、`docs/reference/code-reference.md`。

## 1. 使用方式

1. 先看 §2 的跨模块风险与优先处理建议，那里是影响多个模块、优先级最高的一批。
2. 再按模块查 §3；每条都带来源链接，需要细节时回到原文档。
3. 全部 28 个模块已实现；§3 只列各模块仍存在的改进项。
4. 修改程序后，若解决了某条，请从本文件删除或改为“已完成”。

## 2. 跨模块遗留风险

> 来自 [计划完成情况](plan-status.md) §5。

### 2.1 优先处理建议

按“影响面 × 阻塞后续模块”排序，建议先处理：

1. **M25 流程与菜单**：主菜单/暂停/存档槽/GameOver 已由 M09 接线，菜单按钮支持键盘焦点（方向键/Tab 移动、Enter/空格激活）；农场/林地已是两张独立 40×23 地图，由 `SceneStack::replace` 切换并带 0.4 秒淡入过渡；死亡面板提供复活/读自动存档/读存档槽/主菜单；仍缺淡出式转场与按 `AppState` 自动屏蔽输入；睡眠为体力驱动，没有强制起床/晕倒。
2. **M14 序列化已覆盖玩法段，但仍无通用组件 serializer**：日期/场景位置/背包/快捷栏/装备/农田/金币/出货/加工/叙事/AI/世界对象/玩家生命已能保存并读回；新增组件仍需在 app 手写 `fillSaveContext`/`applySaveFile`。
3. **M24 的后续接线**：金币尚未统一到 `player::Wallet`；商店已有季节库存/每日余量/价格波动，但条目多时列表不可滚动；加工站仍只是字符串；日终结算已由 M25 `endDay()` 编排。
4. **M23 的后续接线**：v1 已有对话/任务运行，play 已接农场 Elder（对话/接取/完成/奖励），且好感/flags/每日上限/任务进度已存档；但只有 1 个 NPC 与 1 条任务，尚未扩 M15 内容表、没有 NPC 日程，且 `OpenShop` 尚未接到 M24。
5. **M09 UI 文本输入/布局/焦点链**：菜单按钮已有键盘焦点链（仅 `button()`），任务日志与背包已有分页/翻页，但 M09 仍无通用滚动区与裁剪，复选框/滑条未入链。
6. **M06 后处理/光照**：M22 只有近似暗化层，没有真正的乘法光照、阴影或渲染目标。
7. **M08 音频流式**：WAV 解码已落地（`decodeWav`，PCM8/16、1–2 声道、线性重采样；`audio.json` 的 `path` 已接 `music_day`/`sfx_harvest`）；仍缺 OGG 解码与音乐流式播放（`MusicStream`）。
8. **M21 寻路预算与 NPC 日程**：大量 agent 同时 A* 会推高固定步；M22 的 `HourChanged` 尚未接到 AI。
9. **M19 品质/产量**：农田整块快照已可存档/读回；品质、产量表与多次收获次数仍未实现。
10. **M26 编辑器范围**：瓦片/组件/区域/对象/实体编辑与地图浏览器（`data/maps/` 扫描/新建/删除）已可用；内容检查器、动画预览与碰撞可视化仍缺。

### M01 Core Foundation

**设计文档**：modules/01-core-foundation.md

已解决

- `Rect` 形态：采用独立结构体（约定见 [编码与内容规范](../architecture/conventions.md)）。
- 日志格式化：使用 1024 字节栈缓冲 + `vsnprintf`，不依赖 `std::format`。
- 错误传递：C++20 下使用自研 `Result<T>`，不启用异常。

仍存在

- 关闭异常后，标准库 OOM 会 terminate；依赖 `setFatalHandler` 给出可诊断信息，但不保证能优雅恢复。
- 日志 sink 固定 8 个槽位且为非拥有指针，调用方必须在 sink 生命周期内先 `removeLogSink`。
- `Result` 的错误路径不带调用栈，定位依赖日志与断言消息。
- `snapToPixel` 在极端大世界坐标下会因浮点精度失准，v1 世界尺寸远小于该阈值，暂不处理。

### M13 物理与碰撞

**设计文档**：modules/13-physics-collision.md

1. **实体对实体只有步首快照**：一步之内两个实体挤进同一格会重叠一帧。若 M20 出现"被怪推着穿墙"，需要加入实体对实体解算或分轴双向求解。
2. **卡住即忽略的副作用**：如果实体的生成位置本来就在墙里，它会一直能穿那面墙，直到离开。放置型玩法（M17）要把生成点校验纳入流程。
3. **子步上限是隐式的**：`delta` 越长子步越多，一次 `move` 的代价线性上升。极端击退（如 1000 px）会切 250 个子步，需要时应在调用侧限制位移。
4. **触发器是 O(触发器数 × 候选数)**：每步全量重算。触发器数量多到几百时需要改成事件驱动的集合增量。
5. **宽相 cell 尺寸未自适应**：64 px 对 16 px 瓦片的场景够用；如果出现大量超大碰撞体（房屋整体盒），`maxCellOccupancy` 会升高，需要按区域调 `setCellSize`。
6. **没有圆形/胶囊碰撞体**：角色用 AABB 在斜向贴墙时会有轻微"卡角"感，靠缩小盒子缓解。
7. **`raycastTiles` 不经过掩码**：瓦片永远算 `World`。若将来有"可穿透地形"的攻击，需要给 `raycast` 增加一个 tile 开关。
8. **未处理坐标极值**：`static_cast<int>(std::floor(...))` 在超大坐标下会溢出。世界尺寸限制在几千像素内时无影响。
9. **每步有少量堆分配**：`queryUnique` 返回新 `vector`，`step` 每帧一次、`move` 每个实体每步一次。100 实体时实测无感，但这是可优化点（预留 scratch 缓冲）。
10. **`PhysicsError` 目前只是文档**：没有 `Result` 返回值，因为移动失败是常态而非异常。若将来需要严格错误上报，要统一改签名。
11. **与存档的关系未定**：`Velocity` 要不要进存档？速度是意图，重进游戏应归零；`Collider` 是配置，应由内容库提供。留给 M14 决定。

与模块文档 §9 对应，这里只列"落地时立刻会碰到"的部分：

1. 实体互推未实现，一步内可能重叠一帧。
2. 生成点若在墙内，该实体会一直能穿那面墙。
3. 每次 `move` 有一次 `vector` 分配（`queryUnique`），100 实体可接受但可优化。
4. 触发器全量重算，触发器上百时需要增量。
5. `PlayerAttack`/`EnemyAttack` 层已定义但尚无使用者——M20 落地时要确认掩码成对配置。
6. `Velocity` 是否进存档未定（M14）。
7. 没有圆形碰撞体，斜向贴墙靠缩小盒子缓解卡角。

- 没有属性面板、内容检查器、动画预览、碰撞层可视化编辑。
- 没有自由相机/缩放；编辑器沿用运行时相机。
- 仅地图新建名称框有物理键文本输入（IME 兜底）；浏览器/编辑器被 app 排除在键盘焦点链外，编辑器内仍只有鼠标，也没有滚动面板。
- 没有自动瓦片重烘焙；编辑后按原 tile id 提取。
- 没有多步命令分组、保存前验证器或独立编辑器进程。
- L 键只验证加载，不替换实时地图。
